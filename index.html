entreprise

Déploiement des postes par métier

Le but : qu'un nouvel employé trouve son poste prêt, avec les logiciels de son métier déjà installés. J'ai d'abord développé mon propre outil en Bash, PostInit : on choisit le métier et le poste, il affiche un récapitulatif, demande de confirmer en tapant le nom du poste, puis installe et journalise chaque étape. Les données de l'entreprise sont séparées du code. Il fonctionne en environnement de test. Puis j'ai commencé à passer à Ansible, avec l'interface web Semaphore.

Appris : la démarche, du besoin à la solution, le Bash, le YAML et Ansible. Et surtout que tout faire soi-même n'est pas toujours la bonne idée : un outil standard est souvent plus fiable et plus simple à maintenir.

bash · ansible · yaml · docker · semaphore

voir le détail

# le besoin

Quand un employé arrive, son poste doit être prêt avec les logiciels de son métier, sans que lui ni son tuteur aient à s'en occuper.

# version 1 : PostInit, mon outil en Bash

  1. Vérifier les prérequis. Mode connu (simulation ou réel), jq installé, inventaire JSON valide, dossier des profils présent. Sinon, l'outil s'arrête avec un message clair.
  2. Choisir le profil métier. Un fichier texte par métier, qui liste ses logiciels.
  3. Choisir le poste cible dans l'inventaire.
  4. Relire le récapitulatif et confirmer en tapant le nom exact du poste, pour éviter d'installer sur la mauvaise machine.
  5. Installer et afficher le résultat de chaque logiciel.
  6. Tout journaliser dans un fichier de logs.

Le code est générique : tout ce qui est propre à une entreprise est dans les données, jamais dans le code. On peut donc le réutiliser ailleurs.

# version 2 : passage à Ansible

Mon prof référent m'a conseillé de ne pas réinventer la roue. J'ai repris la même logique avec Ansible : un inventaire où les postes sont rangés par métier, un fichier par métier avec ses logiciels (installés par winget), et Semaphore comme interface web. J'ai gardé les mêmes sécurités que dans PostInit.

yaml · deploiement.yml (extrait)- name: Refuser un lancement sans --limit
  ansible.builtin.assert:
    that: ansible_limit is defined
    fail_msg: "Lancement refusé : précise le poste avec --limit NOM-DU-POSTE"

- name: Refuser un lancement sur plusieurs postes
  ansible.builtin.assert:
    that: ansible_play_hosts | length == 1
    fail_msg: "Lancement refusé : un seul poste à la fois"

- name: Vérifier la confirmation
  ansible.builtin.assert:
    that: confirmation_poste == inventory_hostname
    fail_msg: "Confirmation refusée : le nom ne correspond pas"

# où j'en suis

PostInit fonctionne en environnement de test, avec des données fictives. La version Ansible est en cours de prise en main. Rien n'est encore utilisé en production.

cheat, aide-mémoires en ligne de commande

Mon propre outil en Bash pour créer, afficher, chercher et éditer des fiches Markdown. Feuille de route : options, page man, complétion, puis un paquet .deb installable avec apt.

Appris : les fonctions Bash, le parsing d'options, les variables d'environnement et les pièges des alias.

# ce qui marche déjà

  • cheat sans argument liste toutes les fiches.
  • cheat -n nom crée une fiche et l'ouvre dans l'éditeur.
  • Une fiche enregistrée vide est supprimée automatiquement.
  • Le dossier et l'éditeur se règlent avec des variables d'environnement.
bash · cheat (extrait)cheat() {
    local dir=${CHEAT_DIR:-$HOME/cheats}    # dossier des fiches
    local editor=${VISUAL:-${EDITOR:-nano}} # éditeur, nano par défaut
    command mkdir -p "$dir"                 # command : ignore les alias

    if [[ -z "$1" ]]; then                  # aucun argument : liste les fiches
        for f in "$dir"/*.md; do
            [[ -f "$f" ]] || continue
            command basename "$f" .md
        done
    fi
}

# difficulté rencontrée

Mon thème de terminal (Oh My Bash) remplaçait certaines commandes par des alias au moment où la fonction était définie, ce qui changeait son comportement. Solution : appeler les vraies commandes avec command.

# feuille de route

  1. Options pour éditer, supprimer, chercher et afficher l'aide, avec des couleurs.
  2. Script autonome avec une page man et l'autocomplétion bash et zsh.
  3. Paquet .deb installable avec apt.

Administrer Windows depuis Ubuntu en SSH

OpenSSH Server sur Windows, connexion par clé ed25519, puis des scripts Bash et PowerShell pour auditer et nettoyer le disque à distance. Résultat : environ 190 Go retrouvés.

Appris : la cryptographie asymétrique en pratique et l'administration multi-OS.

ssh · bash · powershell

voir le détail

# démarche

  1. Côté Windows : installer et démarrer OpenSSH Server, vérifier le pare-feu et le profil réseau.
  2. Côté Ubuntu : générer une paire de clés ed25519 et déposer la clé publique sur Windows.
  3. Tester une connexion sans mot de passe, puis des commandes à distance en une ligne.
  4. Automatiser avec des scripts Bash qui lancent des scripts PowerShell : audit du disque avec seuil d'alerte, nettoyage sûr des fichiers temporaires, analyse de la taille des dossiers.
  5. Documenter le tout dans une procédure réutilisable sur d'autres machines.

# pièges rencontrés

  • Avec un compte Microsoft, la connexion par mot de passe échoue souvent. La clé SSH règle le problème, et c'est de toute façon la bonne pratique.
  • Une commande entre guillemets est interprétée par le shell de Windows, pas par Bash. Avec des guillemets simples, Bash n'y touche pas.
  • Ne jamais lancer à distance une commande qui coupe le réseau ou SSH de la machine : on perd l'accès.

Audit de sécurité de mon site WordPress

Après avoir appris les bases de l'attaque, j'ai audité mon propre site IDEAL, en local. D'abord en attaquant externe (wpscan, dirb, curl et mon propre scanner en Bash), puis en administrateur (WP-CLI). Résultat : 9 failles classées par criticité, chacune avec son correctif. Les plugins périmés sont déjà mis à jour.

Appris : la vue externe ne montre qu'une partie des problèmes, cacher n'est pas sécuriser, et il faut plusieurs barrières plutôt qu'une seule.

wpscan · dirb · curl · wp-cli · bash

voir le détail

# démarche

  1. Poser le cadre. Uniquement mon installation locale, accessible depuis ma machine. Aucune cible tierce.
  2. Regarder de l'extérieur (black box). Comme un visiteur inconnu : versions affichées, extensions visibles, dossiers accessibles, avec wpscan, dirb, curl et mon propre scanner en Bash.
  3. Regarder de l'intérieur (white box). En administrateur, avec WP-CLI, pour avoir la liste exacte des extensions, des comptes et des réglages.
  4. Comparer les deux vues. L'outil externe n'a vu que 3 extensions sur 9 et s'est trompé sur une version. Un vrai audit combine les deux.
  5. Classer et corriger. Chaque faille reçoit une criticité, une preuve et un correctif. Je commence par les plus graves.

# résultats

Ce qui était déjà bien configuré : WordPress et le thème à jour, le fichier de configuration qui ne fuit pas, un mot de passe administrateur robuste, et des fichiers qui appartiennent à un compte de service séparé du mien (moindre privilège).

# difficulté rencontrée

Mon scanner maison considérait qu'une page n'existait pas quand le serveur répondait 404. Mais WordPress ne répond jamais 404 : il redirige tout (code 301). Résultat, mon script affichait toutes les pages comme « trouvées ».

Leçon : un outil doit d'abord mesurer comment le site répond normalement, au lieu de supposer un comportement.

bash · mini-drib.sh#!/bin/bash
url=$1

while read mot; do
    code=$(curl -s -o /dev/null -w "%{http_code}" $url/$mot)
    if [ "$code" != "404" ]; then      # supposition fausse face à WordPress
        echo "$mot $code"
    fi
done <liste.txt

# ce que j'en retiens

  • Cacher une information ne la protège pas.
  • Une seule barrière ne suffit jamais : c'est la défense en profondeur.
  • Un accès administrateur WordPress revient à pouvoir exécuter du code sur le serveur, d'où l'importance de bien protéger la connexion.

# Bandit (OverTheWire)

Un jeu où chaque niveau est une machine Linux à explorer en SSH pour trouver l'accès au niveau suivant. Pour chaque niveau, je note le raisonnement et le mécanisme Linux en jeu (permissions, programmes à droits élevés, réseau, tâches planifiées), jamais les mots de passe, comme le demandent les règles du site.

# DVWA, injection de commande

  1. Comprendre la faille : la page passe ce que tape l'utilisateur directement à une commande système, sans le vérifier.
  2. Niveaux intermédiaires : le code retire certains caractères dangereux (liste noire). J'ai constaté qu'une liste noire oublie toujours un cas.
  3. Niveau le plus protégé : le code n'accepte que ce qui est attendu, ici une adresse IP en 4 nombres (liste blanche). C'est la bonne approche.

Leçon : ne jamais faire confiance à une saisie utilisateur, et préférer autoriser l'attendu plutôt qu'interdire le dangereux.

SecNumCloud devient obligatoire

Un arrêté rend obligatoire, et plus seulement recommandé, un cloud qualifié SecNumCloud par l'ANSSI pour les données sensibles de l'État, en application de la loi SREN de 2024.

Pour une entreprise : Les entreprises qui travaillent pour l'administration sont aussi concernées. Un hébergement qualifié coûte plus cher : il faut d'abord évaluer la sensibilité des données.

OVHcloud et Numspot qualifiés

Deux acteurs français du cloud souverain ont obtenu le même jour la qualification SecNumCloud de l'ANSSI.

Pour une entreprise : Plus de choix pour héberger ses données en France, à l'abri du Cloud Act américain, qui permet aux autorités des États-Unis d'accéder aux données gérées par des entreprises américaines.

Arcep · Data Act européen
fiabilité élevée

Fin des frais pour changer de cloud

À partir du 12 janvier 2027, le Data Act interdit aux fournisseurs de facturer le changement de fournisseur, y compris la sortie des données.

Pour une entreprise : Il devient plus facile de quitter un SaaS ou un hébergeur qui ne convient plus. C'est le moment de vérifier les clauses de réversibilité des contrats.

Études Akamai, Valence Security
fiabilité moyenne

Les API de plus en plus attaquées

87 % des organisations interrogées ont subi au moins un incident de sécurité lié à une API dans l'année, contre 78 % en 2022.

Pour une entreprise : Relier deux logiciels crée un nouveau point d'entrée. Bonnes pratiques : droits minimum pour la clé API, clés jamais en clair dans un script, HTTPS uniquement, échanges journalisés.

Ce que j'en retiens

  1. Le cloud est pratique mais crée une dépendance.
  2. La France impose un cloud souverain pour les données sensibles.
  3. L'Europe facilite le changement de fournisseur.
  4. Relier des logiciels par API demande une vraie sécurisation.
